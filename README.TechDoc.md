# FTP 工具 (C++ 版)

使用 C++ 重写的 FTP 服务器工具，修复了原 Python 版本的权限问题，并扩展了功能。
使用 **Visual Studio 2022 自带的 MSVC 编译器** 构建，无任何第三方依赖。

## 相比原 Python 版本修复的问题

原 Python 版本使用 `pyftpdlib` 的权限字符串，存在以下缺陷：

| 问题 | 原因 | 本版本修复 |
|------|------|-----------|
| 勾选"写入"后仍无法上传/修改 | 权限字符串缺少 `l`（列目录）等必要位，且组合不完整 | 每个权限独立控制，互不干扰 |
| 文件夹无法放入（无法创建目录） | 缺少 `m`（MKD 建目录）权限 | 新增"创建目录"独立权限 |
| 开了读写仍不能修改文件 | 缺少 `f`（重命名）权限 | 新增"重命名"独立权限 |
| 无法删除目录 | 缺少 `d` 之外的目录删除逻辑 | 新增"删除目录"独立权限 |

## 功能特性

- **原生 Win32 GUI**：无需 Python 环境，单文件 exe 直接运行
- **完整权限控制**（7 项独立开关）：
  - 读取（下载 RETR）
  - 写入（上传 STOR/APPE）
  - 删除文件（DELE）
  - 创建目录（MKD）
  - 删除目录（RMD）
  - 重命名（RNFR/RNTO）
  - 列目录（LIST/NLST）
- **实时日志窗口**：显示客户端连接、上传、下载、删除、重命名等操作
- **可绑定指定网卡**：在“其他设置”里选择监听网卡，或保留“全部网卡”兼容多网卡/TUN
- **文件名编码可选**：自动识别、仅 UTF-8、仅 GBK（本地编码），兼顾资源管理器与第三方客户端
- **被动模式端口范围可配置**：默认 50000-50100
- **目录穿越防护**：客户端无法访问共享目录之外的文件
- **多客户端并发**：每个连接独立线程处理
- **支持主动(PORT)与被动(PASV)模式**

## 支持的 FTP 命令

`USER` `PASS` `QUIT` `SYST` `FEAT` `OPTS` `NOOP` `TYPE`
`PWD` `CWD` `CDUP` `PASV` `PORT` `LIST` `NLST`
`RETR` `STOR` `APPE` `DELE` `MKD` `RMD` `RNFR` `RNTO` `SIZE` `MDTM`

## 编译方法

### 方法一：一键脚本（推荐）

双击运行 `build.bat`，或在命令行执行：

```bat
build.bat
```

生成的可执行文件位于 `build\FtpTool.exe`。

### 方法二：CMake

```bat
cmake -B build -G "Visual Studio 17 2022" -A x64
cmake --build build --config Release
```

### 方法三：Visual Studio 直接打开

用 VS 2022 打开 `CMakeLists.txt`（VS 原生支持 CMake 项目），直接生成即可。

## 使用说明

1. 运行 `build\FtpTool.exe`
2. 设置**端口**（默认 21，非管理员权限建议用 1024 以上端口，如 2121）
3. 选择**共享路径**（点击"浏览..."）
4. 按需勾选**权限**
5. （可选）切到**高级模式 → 其他设置**，选择监听网卡和文件名编码
6. 点击**启动服务**
7. 其他设备通过 `ftp://本机IP:端口` 访问

> **提示**：使用 21 端口需要管理员权限。若遇到防火墙拦截，请放行对应端口
> 以及被动模式端口范围（默认 50000-50100）。

## 中文文件名上传失败（550 Cannot create file / errno=22）

**现象**（Windows 资源管理器上传中文名文件时最常见）：

```
响应客户端: 550 Cannot create file: 大数据应用与服务赛项（样�?�?docx
创建文件失败: ...\大数据应用与服务赛项（样棰?锛?docx | errno=22
```

**原因**：客户端把 UTF-8 编码的文件名当成 GBK 转了一圈，再以 GBK 发过来：

- `题`(UTF-8 `E9 A2 98`) → `E9 A2 3F`，`）`(`EF BC 89`) → `EF BC 3F`：
  非法尾字节被替换成 `?`，紧跟其后的 ASCII 字符（`5`、`.`）还会被吞掉；
- 服务端解码后名字里就带上了 `?`，而 `?` 是 Windows 不允许的文件名字符，
  `CreateFileW` 返回 `ERROR_INVALID_NAME(123)`，再被 `ofstream` 映射成
  `errno=22`，于是整个文件都传不上去。

> 字节在客户端就已经损坏，**服务端无法还原**出"题5）"：被换成 `?` 的那个字节和被
> 吞掉的那个字符都已经没了。唯一能确定的是全角括号（见下文"中文括号专项"），可以按
> 配对关系把 `（`/`）` 修回来，其余字符只能保证上传成功。

### 两种兼容模式（高级模式 → 其他设置 → 默认编码）

默认的 `自动 / 仅 UTF-8 / 仅 GBK` 三种模式**不会改写任何文件名**：名字里带
非法字符时照旧报 `550`，并在回复末尾提示可以改用兼容模式。只有显式选择下面
两种模式才会改写落盘的文件名：

| 模式 | 做法 | 本例落盘名字 |
|---|---|---|
| 兼容模式（尝试修复） | 坏括号按配对还原成 `（`/`）`；非法字符替换为**同形全角字符**（`?`→`？`、`:`→`：`…） | `…（样棰？）docx` |
| 兼容模式（跳过解码） | 非法字符替换为**空格**，把无法解码的文字"抹掉" | `…（样棰  docx` |

两种模式都会：

1. 去掉结尾的空格和点（Windows 会静默丢弃它们），并给设备保留名
   （CON、COM1…）加下划线前缀，保证一定能创建成功；
2. 记一条警告日志，例：
   `文件名含 Windows 非法字符，已替换为全角字符: …（样棰?）docx -> …（样棰？）docx`；
3. 客户端随后继续用**原始的坏名字**发 `SIZE`/`RETR`/`DELE`/`RNFR` 时自动回退到
   改写后的名字，不会出现"刚上传成功，紧接着 550 File not found"。

### 中文括号专项（`（）` 变 `锛?`）

资源管理器对全角括号的处理最容易出问题：`（`=`EF BC 88`、`）`=`EF BC 89`，
第三个字节被它换成 `?`，服务端收到的是 `EF BC 3F`，按 GBK 解码就成了"锛"加一个
非法字符 `?`——名字里出现 `锛？` 这种乱码就是这么来的。

- **兼容模式（尝试修复）**：按括号配对把 `EF BC 3F` 还原成 `（` 或 `）` ——
  前面还有没配对的 `（` 就补 `）`，否则补 `（`。实测 `测试（1）` 被转坏后落盘为
  `测试（）.txt`；
- **兼容模式（跳过解码）**：整段 `EF BC 3F` 抹成一个空格，落盘为 `测试  .txt`。

> 括号后面紧跟的那个字符（如 `（1）` 里的 `1`、`）.docx` 里的 `.`）在客户端做
> GBK 转换时就被非法尾字节吞掉了，服务端**无法恢复**——只能把括号本身修回来，
> 让名字可读、可创建。要保留完整原名，请改用 UTF-8 客户端或在服务器上改名。

模式对运行中的服务立即生效，改完点"保存"即可，不用重启。

### 想要原名？改客户端

- 客户端设为 **UTF-8** 传输：FileZilla → 站点管理器 → 字符集 → "强制 UTF-8"；
  命令行 `lftp` 加 `set ftp:charset utf-8`；
- 本工具的客户端：连接时勾选 **UTF-8**（`OPTS UTF8 ON`）；
- 也可在上传后到共享目录里直接改名（文件不会丢）。

> **资源管理器**：它不使用 UTF-8 上传，遇到中文名容易把编码转坏。建议用
> FileZilla 等客户端；必须用资源管理器时，选"兼容模式（跳过解码）"最省事。

### 本工具客户端 ↔ 本工具服务端

两边都用本工具时，客户端连上后会先协商 `OPTS UTF8 ON`，之后文件名统一按同一种
编码收发，不会出现资源管理器那种"名字从中间坏掉"的情况。实测（`tests/client_loopback.cpp`，
上传 → 列表 → 下载 → 删除全流程，覆盖 5 种默认编码）：

| 服务端默认编码 | 客户端实际使用 | 中文名 | emoji 等 GBK 表示不了的名字 |
|---|---|---|---|
| 自动 / 仅 UTF-8 / 兼容模式（3、4） | UTF-8 | 原样往返 | 原样往返 |
| 仅 GBK | GBK | 原样往返 | 客户端提前拦下并提示，不会发出 `?` |

- 服务端在"仅 GBK"模式下对 `OPTS UTF8 ON` 回 `502`（而不是 `200`）。以前回
  `200` 会让客户端误以为已经切到 UTF-8，把 UTF-8 名字发过来后被服务端按 GBK
  解码，反而自己制造出带 `?` 的非法文件名（`550` / `errno=22`）。
- 反过来，服务端是 GBK 而名字里有 GBK 表示不了的字符（emoji、部分生僻字）时，
  客户端会**提前报错**，提示改用 UTF-8 或改名，而不是发一条注定失败的命令。


## 关于杀毒软件误报（360 / 火绒 / Windows Defender）

本程序是**完全开源、无恶意行为**的 FTP 服务器工具，但可能被杀毒软件误报为木马。
这是**误报**，常见原因：

1. **无数字签名**：自编译的 exe 没有代码签名证书，杀软对未知程序默认警惕
2. **网络监听行为**：程序会监听端口（`bind`/`listen`），这是木马常见特征，触发启发式检测
3. **无信誉记录**：新编译的文件在杀软的云查杀库中没有信誉数据

### 解决方案

**方案一：添加信任（推荐）**
- 360：打开"360安全卫士" → "木马查杀" → "信任区" → 添加 `FtpTool.exe` 所在目录
- 或右键托盘图标 → "恢复区" → 找到被隔离的文件 → "恢复并信任"

**方案二：临时关闭实时防护**
- 编译和运行时临时关闭杀软实时防护，用完再开启

**方案三：自行编译**
- 由于源码完全可见，你可以自己运行 `build.bat` 编译，本地编译的 exe 通常不会被拦截

**方案四：提交误报申诉**
- 360 误报申诉：https://open.360.cn/report.html
- 提交后一般 1-3 个工作日会解除误报

> 提示：本程序不包含任何后门、不联网上传数据、不修改系统设置。
> 所有代码都在 `src/` 目录下，可自行审查。
